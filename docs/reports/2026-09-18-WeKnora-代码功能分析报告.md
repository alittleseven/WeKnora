> 分析对象：`Tencent/WeKnora` 个人 fork 本地检出（`local-custom` 分支，基线 v0.8.0）
> 分析方式：本地代码全量探索（后端 / RAG 管线 / Agent 系统 / 前端 / 集成部署 五路并行深挖）

---

## 1. 项目定位与总体形态

WeKnora 是腾讯开源的、LLM 驱动的企业级知识库框架，围绕四大核心能力组织：

1. **RAG 快问快答** —— 多源文档摄取 → 解析 → 切分 → 向量化 → 混合检索 → 重排 → 带引用的回答；
2. **ReAct Agent** —— 自主编排知识检索、MCP 工具、租户技能、会话级持久沙箱（Docker/E2B/Cube）、Web 搜索，完成多步任务；
3. **Wiki 模式** —— Agent 把原始文档蒸馏成自维护、互链的 Markdown 知识库 + 可视化知识图谱，支持手工编辑、版本历史、一键回滚；
4. **跨会话长期记忆** —— profile/preference/fact/task/interest 五类记忆自动抽取、用户确认、检索注入。

**技术栈与仓库形态：**

| 目录 | 技术 | 职责 |
|------|------|------|
| `cmd/server` + `internal/` | Go（gin + GORM + asynq + uber/dig） | 后端主体（API、任务队列、Agent 引擎） |
| `docreader/` | Python gRPC 服务 | 文档解析（PDF/Office/图片/XMind 等） |
| `frontend/` | **Vue 3.5** + TS + Vite 7 + Pinia + TDesign | Web 前端（注意：是 Vue，不是 React） |
| `mcp-server/` | Python（mcp 2.x 高层 API） | 对外 MCP Server，31 个工具 |
| `cli/` | Go | `weknora` CLI（agent-first JSON 契约） |
| `client/` | Go SDK | 供 CLI 与第三方 Go 集成复用的 API 客户端 |
| `cmd/desktop` | Wails v2 | "WeKnora Lite" 桌面壳（内嵌后端） |
| `miniprogram/` | 原生小程序 | 微信端问答 |
| `docker-compose.yml` / `helm/` / `deploy/` | — | 完整模式约 20 个服务编排 / K8s / systemd |

数据库：生产 PostgreSQL（paradedb 镜像），Lite 版 SQLite + sqlite-vec；迁移用 golang-migrate，SQL 在 `migrations/versioned`（206 组 up/down，另有 mysql/paradedb/sqlite 方言变体）。

## 2. 整体架构与后端骨架

### 2.1 启动流程与依赖注入

- 入口 `cmd/server/main.go`：设 gin mode → runtime 容器准备 → **`container.BuildContainer`**（`internal/container/container.go`，1937 行，基于 **uber/dig**）→ 启动期 bootstrap（如提升系统管理员）→ `Invoke` 创建 `http.Server` → `listenWithRetry` 绑端口 → 订阅 Redis 配置广播 → 双信号优雅停机。
- DI 注册顺序：基础设施（config / DB / 文件服务 / Redis / **ants 协程池**）→ 41 个 `repository.New*` → 59 个 `service.New*`（含 dig.Name 命名的 TaskHandler）→ 38 个 `handler.New*` → `router.NewRouter`；随后 `Invoke` 启动 asynq server、housekeeping、约 20 个**聊天管线插件**（`chatpipeline.NewPlugin*`）、审计日志保留任务等。
- `cmd/desktop/main.go` 是 Wails v2 壳（内嵌反向代理 + 自动更新）；`cmd/download` 为构建期下载 DuckDB 扩展（spatial/excel，供数据分析工具用）。

### 2.2 路由与分层

- `internal/router/router.go`：中间件链 = CORS → RequestID → Language → Logger → Recovery → ErrorHandler →（IM 回调 / embed 公开路由 / MCP server / 沙箱 WS 这些自带鉴权的先挂）→ `middleware.Auth` → Langfuse → 审计服务；`/api/v1` 分组后经 **API key 策略闸**，再按域拆分到 `routes_auth_tenant.go / routes_knowledge.go / routes_chat.go / routes_agent.go / routes_infra.go / routes_mcp_endpoint.go / routes_memory.go` 等文件**手工注册**（非自动生成）。启动期 `assertAPIKeyPoliciesMatchRoutes` 校验 API key 策略与路由模板一致。
- 分层模式：**handler → application/service → repository → GORM**。`internal/handler` 有 58 个非测试 go 文件，覆盖 auth/tenant/knowledgebase/knowledge/chunk/faq/session/message/model/mcp/sandbox/skill/datasource/wiki/memory/embed/im/system 等。
- **典型全链路例 1（知识上传）**：`POST /api/v1/knowledge-bases/:id/knowledge/file`（守卫 `OwnedKBOrAdmin + KBAccessWrite`）→ `handler/knowledge.go CreateKnowledgeFromFile` → `service/knowledge_create.go` → GORM 落 `knowledge` 表 → asynq `TypeDocumentProcess` → worker 消费 `ProcessDocument`。
- **典型全链路例 2（问答）**：`POST /api/v1/knowledge-chat/:session_id` → `handler/session/qa.go KnowledgeQA → executeQA` → `service/session_knowledge_qa.go` → chat_pipeline 插件链（Search/Rerank/MemoryRecall/ChatCompletionStream…）→ message 持久化 + SSE 推流。

### 2.3 核心数据模型（`internal/types`）

`Tenant`（含 RetrieverEngines/StorageQuota/ContextConfig 等 jsonb）、`User`（IsSystemAdmin）、`KnowledgeBase`（CreatorID + `VectorStoreID` 向量库绑定，GORM `<-:create` 只读）、`Knowledge`（ParseStatus/PendingSubtasksCount）、`Session`（ParentSessionID 支持会话分叉 fork）、`Message`、`AgentConfig`、`TenantAPIKey`、`AuditLog`、`WikiPage`、`Memory`、`Chunk`/`ChunkRevision`、`EmbedChannel`、`StorageBackend` 等。

### 2.4 任务队列与 worker pool 治理（`internal/router/task.go`）

基于 **asynq（Redis）**，装配 6 个命名 server：**core（解析）/ postProcess / enrichment（摘要/多模态/图谱）/ maintenance / shared（弹性层，借空闲容量同时订阅 core+enrichment，Redis 原子 dequeue 保证单次执行）/ wiki（硬隔离并发）**。约 20 个任务类型注册在单 mux（`TypeDocumentProcess`、`TypeWikiIngest/Finalize`、`TypeMemoryExtract`、`datasource:sync` 等）。

- **失败治理**：asynqdl 死信中间件为耗尽重试的任务写 `task_dead_letters` 表并回调把 `knowledge.parse_status` 翻为 failed；wiki 锁冲突固定 15s 重试、其余指数退避；启动时 `resetPendingTasks` / `recover_pending_wiki_tasks` 重置卡死任务。
- **per-model 并发 governor**：`internal/models/limiter/governor.go` 进程级单例，只对打标的后台任务限流，模型自身 MaxConcurrency 优先，支持运行时热调（system_settings）。

### 2.5 配置系统

`internal/config/config.go` 一级段：Conversation/Server/KnowledgeBase/Tenant/Auth/OIDCAuth/Models/VectorDatabase/DocReader/StreamManager/ExtractManager/WebSearch/PromptTemplates/IM/Agent。`.env.example`（788 行）按 A–J 分组：部署基础 / 数据与存储 / 检索与图谱 / 模型 / 文档解析 / 认证与空间隔离 / Agent 与沙箱 / 可选集成 / 可观测性 / 安全与调优。Lite 模式 `.env.lite.example` 仅 93 行。

## 3. 重点功能一：文档摄取与 RAG 检索管线

### 3.1 数据源接入（8 连接器，`internal/datasource/`）

- 连接器实现：`feishu`（core/drive/wiki 三子包，wiki 懒加载树）、`notion`、`yuque`、`gitlab`、`confluence`、`dingtalk`、`rss`、`ima`（腾讯 ima）。
- 统一接口 `datasource/connector.go`：`Validate / ListResources(parentID 懒加载) / FetchAll / FetchIncremental`；扩展 `StreamConnector.FetchFullStream`（逐条 Emit + 分页 Checkpoint 持久 cursor，防超时重扫）。
- **调度**：`scheduler.go` 用 robfig/cron 按 `SyncSchedule` 定时入队，双去重（HasRunningSync 防重叠 + asynq 确定性 TaskID）；手动同步走 `DataSourceService.ManualSync`。全部汇入 asynq 任务 `datasource:sync`，由 `ProcessSync` 消费：选 connector → 全量/增量 → 转成 Knowledge（**复用上传管线**）→ `sweepStaleSubtree` 对账删除。无 webhook，纯拉模式。

### 3.2 文档解析（docreader gRPC + Go 侧引擎注册表）

- **docreader 是 Python gRPC 服务**（`docreader/main.py`，proto 含 Read/ReadStream/ListEngines，TLS+Token 鉴权）。Go 侧客户端 `internal/infrastructure/docparser/grpc_parser.go`。
- Python 侧 `parser/registry.py` 按"引擎→扩展名→Parser 类"注册：builtin 引擎覆盖 docx/pdf/md/xlsx/pptx/epub/html/mhtml/xmind/图片；另有 markitdown、opendataloader（PDF 版面分析）引擎。
- **Go 侧引擎注册表** `docparser/engines.go` 定义 8 引擎：`builtin`（转发 docreader）、`simple`（Go 原生文本/图片）、**`anydoc`（进程内 cgo Office 转换器**，`anydoc/backend_cgo.go`，可用时优先于 builtin）、`weknoracloud`（HTTP 云端解析）、`mineru/mineru_cloud`、`paddleocr_vl/paddleocr_vl_cloud`（自建/云端 OCR-VL 版面解析）。
- **图片 OCR/Caption 是摄取后异步任务**：`service/image_multimodal.go` 入队 `TypeKnowledgePostProcess`，用 VLM 生成 caption 后回写 chunk。

### 3.3 切分：自适应分级 chunking（Go 实现，`internal/infrastructure/chunker/`）

- `profiler.go` 先算 `DocProfile`（标题密度 / 编号章节 / 表格代码占比 / 语言）→ `strategy.go resolveChainWithProfile` 选 tier 链（**heading → heuristic → recursive → legacy**）→ 每级产出经 `validator.go ValidateChunks` 校验失败即降级 → 兜底 `splitter.go SplitText`（递归分隔符 + 受保护正则，默认 ChunkSize=512 / Overlap=80）。
- parent-child 策略由 `knowledge_process.go buildParentChildConfigs` 配置；`KBChunkingDebug` 前端组件可实时预览切分效果。Python `docreader/splitter/` 仅 docreader sidecar 保留。

### 3.4 向量化与索引

- **Embedder 抽象**：`internal/models/embedding/embedder.go`（Embed/BatchEmbed/GetDimensions）+ 工厂；供应商 openai/azure/aliyun/volcengine/zhipu/gemini/jina/nvidia/ollama/weknoracloud，附并发、langfuse、批量 wrapper。跨 KB 检索强制同 embedding 模型（`validateSameEmbeddingModel`）。
- **向量库驱动**：`types/retriever.go RetrieverEngineType` 支持 postgres(pgvector)/elasticsearch(qdrant… 实际 11 种：postgres/elasticsearch/qdrant/milvus/weaviate/doris/sqlite/tencent_vectordb/opensearch/infinity/elasticfaiss)+neo4j 图驱动；各驱动在 `application/repository/retriever/<engine>/repository.go` 实现 `Retrieve/VectorRetrieve/KeywordsRetrieve/Index/Delete`。
- **pgvector HNSW 按维度部分索引**：`migrations/versioned/000002/000059` 中 `CREATE INDEX ... USING hnsw ((embedding::halfvec(N)) halfvec_cosine_ops) WHERE dimension=N`；查询侧设 `hnsw.ef_search`、`iterative_scan=strict_order`，TopK 上限 200。
- **引擎组装**：`service/retriever/factory.go CreateRetrieveEngineForKB` + `composite.go CompositeRetrieveEngine`（vector+keywords 组合，`keywords_vector_hybrid_indexer.go` 双写）；KB 的 `IndexingStrategy` 控制向量化/关键词/图谱开关。

### 3.5 检索与重排（`service/knowledgebase_search.go`）

`HybridSearch` 主流程：归一 MatchCount → 批量加载 KB → 鉴权 → 校验同 embedding → **一次性算 query embedding（避免跨 KB 重复调用）** → `resolveStoreGroups` 按 `(VectorStoreID, ownerTenant)` 分组（即 **KB fan-out 单元**）→ `retrieveFromStores` 用 errgroup 并发多 store（跨引擎分数用 `normalizer.go` 归一、多 store 超时预算）→ `classifyRetrievalResults` 分向量/关键词两路。

- **融合**（`knowledgebase_search_fusion.go`）：单路 `deduplicateByScore`（BM25 无界分数 `rescaleUnboundedScores` 折到 [0,1]）；混合用 **加权 RRF（倒数排名融合）**，k 与权重取自租户 RetrievalConfig。FAQ KB 有迭代扩 TopK 逻辑。
- **重排**：聊天管线插件 `chat_pipeline/rerank.go PluginRerank`；供应商 `internal/models/rerank/`：volcengine/lkeap/jina/aliyun/nvidia/zhipu/weknoracloud，`Reranker` 接口 + 工厂分发。

### 3.6 文档生命周期状态机

`ParseStatus`：**pending → processing → finalizing → completed / failed / deleting / cancelled**（另有 SummaryStatus、EnableStatus、ErrorMessage）。

管线：上传（FromFile/FromURL/FromPassage）入队 → `knowledge_process.go:3340 ProcessDocument`：幂等/删除短路 → SSRF 校验+下载 → 解析 → `processChunks`（清旧 chunk/索引/图谱 → 构造 Chunk（parent-child、图片子 chunk）→ embedding → CompositeRetrieveEngine.Index）→ `finalizeIndexedKnowledgeState`（无多模态任务即 completed，否则等 post-process）。摘要/问题生成是独立任务（`ProcessSummaryGeneration`/`ProcessQuestionGeneration`）。失败由 asynq 重试，`isLastRetry` 才置 failed。重解析 `ReparseKnowledge` + per-文档 `ResolveProcessConfig` 覆盖配置。

**解析 trace 时间线**：`service/knowledge_span_tracker.go SpanTracker`（OpenAttempt → BeginStage/BeginSubSpan → Finalize/Abort），持久化到 knowledge_span 表；前端 `knowledge-processing-timeline.vue` 渲染 Langfuse 风格 span 树。

### 3.7 知识库管理

- **树形文件夹**是**虚拟树**：`types/knowledge_folder.go` 由各文档 `RelativePath` 聚合（`BuildKnowledgeFolderTree`），非物理表；移动/克隆见 `service/knowledge_clone_move.go`。
- **chunk 编辑与版本**：`Chunk.ContentRevision` 每次编辑/回滚递增，`ChunkRevision` 为不可变快照（(chunk_id, revision) 唯一索引）；`service/chunk.go UpdateDocumentChunk`（校验图片一致性）→ `updateChunkVector` 同步重建向量；`RevertDocumentChunk` 回滚。

## 4. 重点功能二：Agent 系统

### 4.1 ReAct 引擎（`internal/agent/engine.go`）

- 配置模型 `types/agent.go AgentConfig`：MaxIterations（负数=无限轮）、AllowedTools 白名单、KnowledgeBases/KnowledgeIDs、SystemPrompt、MCPSelectionMode/MCPAuthWaitTimeout、Thinking、CitationEnabled、SkillsEnabled/AllowedSkills、PinnedMCPServiceIDs/PinnedSkillNames、MaxCompletionTokens/MaxToolOutputChars/MaxContextTokens/CompactionKeepRecentTokens 等。
- `AgentEngine` **无状态跨轮**（历史由 `service.LoadAgentHistory` 重建）。主循环：`Execute → executeLoop → runReActIteration`，每轮 = manageContextWindow 压缩 → drainSteerMessages 中途插话 → **Think**（`think.go callLLMWithRetry`，流式到 EventBus）→ **Analyze**（`observe.go analyzeResponse`，无 tool_calls 即终局）→ **Act**（`act.go executeToolCalls`）→ **Observe**（appendToolResults/Images）。鲁棒性：连续相同内容卡死检测、空回答重试、上下文溢出一次性 compact-and-retry。
- **工具并行**：`executeToolCallsParallel` errgroup 限 8 并发，`CanRunConcurrently` barrier 隔离写工具，保序回填。
- **流式组织**：`internal/stream/factory.go NewStreamManager`（memory/Redis 双实现，含 Steer 插话队列）；`internal/event` EventBus 事件：agent.query/step/tool/complete、thought/tool_call/tool_result/final_answer、tool_approval_required/resolved。

### 4.2 工具体系

- 注册中心 `agent/tools/registry.go`（RegisterTool/RegisterDeferredTool/ExecuteTool）。
- **装配即裁剪**：`service/agent_service.go registerTools` 以 AllowedTools 为源，按能力过滤——无 KB 删检索/wiki 工具、WebSearchEnabled 才注入 web_search/web_fetch、记忆可用才注入 search_memory、共享只读 agent 删写工具、沙箱文件/shell 工具按后端能力注册。
- 内置工具 30+：knowledge_search、grep_chunks、list_knowledge_chunks、query_knowledge_graph、get_document_info、search_conversations、search_memory、**database_query / data_analysis(DuckDB) / data_schema**、web_search/web_fetch、read_file、thinking、todo_write、shell_exec、沙箱文件读写、技能文件读写、wiki 10 个、浏览器技能、discover_mcp_tools/call_mcp_tool。
- **@Skill/@MCP mention 作用域**：`SetPinnedMentions` 设本轮 pin，prompts 以 `<must_use>` 注入用户消息。

### 4.3 MCP 双向集成

- **作为 Client**（`internal/mcp/`）：mcp-go 封装，`MCPManager` 按 service+principal 缓存连接；**OAuth2 全流程**（StartAuthorization/CompleteAuthorization/Revoke + token 持久化），`OAuthRequiredError` 触发**对话内授权等待**；**Human-in-the-loop 审批**（`agent/approval/gate.go RequestAndWait`）发 `tool_approval_required` 事件挂起，Redis pub/sub 支持跨实例 Resolve。
- **对外暴露**：
  - Go 原生 MCP server（`internal/mcpserver/server.go`）：endpoint token 鉴权 + KB 作用域 + 限流，retrieve/ingest/ask/wiki 四组工具；`MCPEndpoint` 持 TokenHash + KnowledgeBaseIDs + Tools 白名单。
  - Python MCP Server（`mcp-server/weknora_mcp_server.py`）：**31 个 @mcp.tool**（租户 CRUD、知识库 CRUD、hybrid_search、create_knowledge_from_file/url/text、knowledge/model/session CRUD、chat/agent_chat SSE、chunk 管理、wiki 检索）；stdio/SSE/HTTP 三传输；对接 Go 后端走 `X-API-Key` 头调 `/api/v1` REST，作用域由租户 API Key 体系控制。

### 4.4 沙箱运行时（`internal/sandbox/`）

- 三后端：`docker_remote_client.go`、`e2b_remote_client.go`、`cube_remote_client.go`；接口层定义 `Sandbox/Manager` + `Config`（含 `Network RemoteNetworkPolicy`）。
- **会话级持久沙箱**：`session_manager.go SessionBoundManager`（每请求按 TenantSandboxConfig 构建）；`session_binding_redis.go` 记录 session↔远端沙箱绑定（turn lease、失效锁）；`ExecuteOnHandle` 复用持久句柄不销毁；Docker 侧 idle_sweeper / orphan_reaper 回收。
- **per-tenant 网络策略**：Restricted=默认拒绝+域名白名单；Docker networkMode 隔离；`url_guard.go` 出网防护。
- **技能 per-sandbox 快照**：`skill_image.go` 指纹校验快照归属（失配回落基础模板），技能写入镜像路径 `/opt/weknora/tenant/skills`；代码执行工具 `shell_exec.go` 按 skill_name 选技能环境（自动 venv、`$WEKNORA_SKILL_DIR`）、命令黑名单校验、stdout/stderr 独立截断保头尾。

### 4.5 租户技能目录（tenant skill catalog）

- **安装**：`service/tenant_skill_source.go InstallSkillFromSource` 支持 ClawHub（`@owner/slug`、`slug@version`）、SkillHub、skills.sh、GitHub/GitLab URL、直连 zip；安装时由**内置安装 agent** 用 write/edit_skill_file + 安装专用 shell 写入快照镜像（有实时进度）。
- 技能结构：SKILL.md（YAML frontmatter，宽松解析第三方缩进）+ scripts/ + resources/。
- **运行时渐进披露（Progressive Disclosure）**：`agent/skills/manager.go` 只注入元数据，`LoadSkill` 按需载全文；SkillSource 双实现（本地目录 / TenantSkillSource zip 缓存）。

### 4.6 跨会话长期记忆

- 五类 `types/memory.go MemoryKind*`：Profile/Preference/Fact/Task/Interest（interest 由主题计数派生）。
- **自动抽取**：回答完成后 `qa.go ScheduleExtraction` → asynq `TypeMemoryExtract` → `memory/extract.go` 用 JSON 行 prompt（输出 `{"action":"add|update|delete","kind":...}`）+ 已有记忆上下文去重更新。
- **确认流程**：系统推断的写入 `MemoryStatusPending` 待确认，用户明说的立即 active；`ConfirmItem` 确认；容量上限 `enforceCapacity` 自动遗忘。注入：`Recall` 组装 memory envelope 进 system prompt；检索走 `search_memory` 工具（lexical + vector 双路）。

### 4.7 Wiki 模式

- **异步生成管线**：文档入库后 `wiki_ingest.go EnqueueWikiIngest` → `ProcessWikiIngest` 批处理：mapOneDocument → 实体/概念抽取（NoUpsert）→ slug 归并 → 引用挂接 → LLM 去重 → `ProcessWikiFinalize` 重建 index/链接（linkify）。Prompt 集 `agent/prompts_wiki.go`（目录规划/摘要/知识抽取/引用/增量修订"compiler not writer"/索引）。
- **知识图谱**：`service/wiki_page.go GetGraph` 从页面 wiki 链接建图，支持 overview / ego（BFS）视图与类型过滤。
- **版本/回滚**：`WikiPageRevision` 快照 + `RevertPageToVersion`；前端行级 diff（`wikiLineDiff.ts`）+ 浏览器内手工编辑。

### 4.8 LLM 供应商抽象与可观测性

- 工厂 `models/chat/chat.go NewChat`：Local→Ollama；Remote→统一 openai 兼容 `RemoteAPIChat`（**Anthropic 独立 Messages 协议**）；统一叠加 debug/langfuse/并发三层 wrapper。

## 5. 认证、多租户与权限

- **登录**：用户名密码（复杂密码可选拨略 `service/password_policy.go`）+ OIDC 完整流程（nonce cookie、JWKS 校验）+ 邀请制注册。
- **鉴权中间件** `middleware/auth.go`：Bearer JWT 或 `X-API-Key`；`resolveTargetTenant` 处理 `X-Tenant-ID` 跨工作区头；embed 外部用户独立 JWT 通道。
- **多工作区 RBAC**：`types/tenant_member.go TenantRole` 四级（owner 40 / admin 30 / contributor 20 / viewer 10），`HasPermission` 级别比较；`middleware/rbac.go RequireRole / RequireSystemAdmin / RequireOwnershipOrRole`（CreatorLookup 回调判创建者）；子资源（chunk/FAQ/wiki）经 `KBCreatorLookupFromKnowledgeID` 回溯父 KB 判权；`EnableRBAC=false` 时只告警不拒绝（向后兼容）。
- **per-KB ownership**：`KnowledgeBase.CreatorID` + KB 组织共享（`service/kbshare.go`）+ `KBAccessRead/Write` 守卫。
- **Scoped API Keys**（fail-closed 设计）：`TenantAPIKey{ScopeType(tenant/platform), FullAccess, KnowledgeBaseIDs, Capabilities}`；capability 枚举 retrieve/chat/ingest/manage_kbs/manage_agents/manage_models/manage_mcp_services 等；`middleware/api_key_gate.go APIKeyRouteAuthorizer` 按 (method, path) 注册路由策略，**未声明路由默认拒绝**。
- **审计**：`audit_logs` 表（1 分钟滑动去重）+ 否决日志 + 保留期清理。

## 10. 总体评价

- **工程成熟度高**：DI 容器管理 140+ 构造器、6 池 asynq 任务治理（弹性共享池 + 死信 + 热调并发）、206 组版本化迁移、契约测试固化的 CLI wire format——是按生产级标准演进的代码库（0.8.0 已含大量安全加固与多实例能力）。
- **扩展点设计一致**：连接器（Connector）、解析引擎（engines）、向量库（RetrieverEngineType）、rerank/embedder/chat provider、文件服务（8 provider）、IM Adapter、沙箱后端——全部是"接口 + 注册表/工厂"模式，替换成本低，这也是它宣称"全模块可换"的代码基础。
- **两条主线清晰**：RAG 管线（摄取态）与 Agent 引擎（交互态）在 chat_pipeline 插件层汇合；Wiki/记忆/摘要等多模态能力全部挂接在 asynq 异步任务上，不阻塞主链路。
- **对二次开发的启示**：本地定制（local-custom 分支）应优先利用其配置驱动面（builtin_models/builtin_agents/prompt_templates/config.yaml）与 Connector/Provider 扩展点，避免改动 internal 核心，以降低与 upstream 合并的冲突面——这与本仓库 AGENTS.md 的分支策略一致。
