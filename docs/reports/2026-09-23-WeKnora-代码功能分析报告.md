## 1. 项目定位与总体架构

WeKnora 是腾讯开源的 LLM 驱动企业级知识库框架，四大核心能力：**RAG 快问快答**（多源摄取→解析→切分→向量化→混合检索→重排→带引用回答）、**ReAct Agent**（自主编排知识检索/MCP 工具/租户技能/会话级持久沙箱/Web 搜索）、**Wiki 模式**（Agent 蒸馏原始文档为自维护互链知识库+图谱）、**跨会话长期记忆**（五类记忆自动抽取、用户确认、检索注入）。

| 目录 | 技术 | 职责 |
|------|------|------|
| `cmd/server` + `internal/` | Go（gin + GORM + asynq + uber/dig） | 后端主体（API、任务队列、Agent 引擎、检索） |
| `docreader/` | Python gRPC | 文档解析服务（PDF/Office/图片/XMind 等） |
| `frontend/` | Vue 3.5 + TS + Vite 7 + Pinia + TDesign | Web 前端 |
| `mcp-server/` | Python（mcp 2.x） | 对外 MCP Server，33 个工具 |
| `cli/` + `client/` | Go | weknora CLI 与 Go SDK |
| `cmd/desktop` | Wails v2 | "WeKnora Lite" 桌面壳（内嵌后端） |
| `miniprogram/` | 原生小程序 | 微信端问答 |
| `docker-compose.yml` / `helm/` / `deploy/` | — | 完整模式 22 个服务编排 / K8s / systemd Lite |

数据库：生产 PostgreSQL（paradedb 镜像），Lite 版 SQLite + sqlite-vec；迁移 golang-migrate，SQL 在 `migrations/versioned`（220 组 up/down，含 mysql/paradedb/sqlite 方言变体）。

分层模式：**handler → application/service → repository → GORM**；`internal/handler` 60 个非测试文件，`internal/application/service` 142 个非测试文件。

### 2.3 本模块实现要点

1. 中间件顺序不可随意调整：Auth 之前的自鉴权路由（IM/MCP/embed/WS）依赖"未被全局 Auth 拦截"；APIKeyGate 必须先于 Register* 挂到 v1，否则子组不继承；新增 /api/v1 路由若不通过 `apiKeyGroup` 声明策略，API Key 调用会被默认拒绝。
2. API Key 是独立于 RBAC 的第二套权限体系：`RequireRole` 对 API-key principal 直接短路放行（middleware/rbac.go:75），真正授权只在 APIKeyGate；改路由路径必须同步策略模板，启动断言会 panic。
3. SSE 是"写缓冲 + 100ms 拉取"而非 channel 推送：事件先落 StreamManager，连接层只轮询——断线续传天然可行，但改事件结构必须兼容旧序列化数据（helpers.go:218-229 已有 map 回退）。
4. 双形态（Redis/Lite）贯穿全层：任务队列、限流器、StreamManager、resetPendingTasks 行为都随 `REDIS_ADDR` 分叉；新增后台能力必须同时考虑两种模式。
5. 鉴权失败语义精细：JWT 无效但 API Key 有效仍可通过（auth.go:148-171）；无租户返回 409 而非 401（auth.go:219）；孤儿空间自愈与 fail-open 分支是历史兼容路径。

## 3. 文档摄取管线（数据源 → 解析 → 切分 → 索引）

### 3.1 功能清单

1. 8 类数据源连接器（feishu 含 core/drive/wiki 三子包、notion、yuque、gitlab、confluence、dingtalk、rss、ima），统一 `Connector` 接口
2. 连接器能力分层：`StreamingConnector`（流式）/ `FullSyncWithCursor`（带基线全量）/ `FullStreamingConnector`
3. 增量同步 cursor 检查点：分页持久化、断点续扫
4. cron 调度 + 双层去重（DB HasRunningSync 防重叠 + asynq 确定性 TaskID 防多实例重复入队）
5. 同步执行 ProcessSync：流式优先、批量兜底、删除对账、失败也落 cursor
6. 文件上传 API：multipart 上传 + 体积前置限制 + 文件哈希去重
7. URL 抓取：网页解析与文件下载双模式，SSRF 两道防线（创建时 + worker 侧复检防 DNS 重绑定）
8. 解析引擎注册与选择：Go 侧 8 引擎 + anydoc 类型级默认覆盖
9. Python docreader gRPC 服务：Read/ReadStream 流式分帧/ListEngines，引擎注册表 builtin+markitdown+opendataloader
10. 自适应切分：profiler 文档画像 → heading→heuristic→legacy 降级链 + validator 校验触发降级
11. parent-child 父子切分：父块只入库不向量化，子块挂 ParentChunkID
12. 六池 asynq 拓扑 + shared 弹性层原子消费
13. 死信中间件 asynqdl：重试耗尽落库 `task_dead_letters` 并回调将 Knowledge 置 failed
14. 后台任务 per-model 并发 governor：仅门控摄取/富化 LLM 调用
15. 知识处理状态机：pending→processing→finalizing→completed/failed/cancelled/deleting，`pending_subtasks_count` 原子归零晋升
16. 多模态图片富化 fan-in：Redis 计数器先行种子 + 图片 OCR/Caption 子任务
17. 摄取后富化：摘要、问题生成（按批）、自动打标、图谱抽取、wiki ingest 入队
18. 卡住任务提示：20 分钟无进展 stall verdict（区分 queued 积压与真卡死）
19. housekeeping 滞留行回收：processing/finalizing 卡行、stranded deleting 行、stallSite 定位
20. wiki finalizing 释放：终态跳过路径立即释放槽位 + rearmWikiTriggers 重臂触发器
21. 未运行阶段级联取消：上游失败把下游 pending 阶段置 cancelled
22. 图片绑定文档：解析提取图片绑定 resource binding，防跨空间浏览 404
23. asynq 级超时护栏与 wiki 锁冲突 15s 固定退避

### 3.2 实现详解

**数据源连接器与调度**。统一接口 `Connector`（internal/datasource/connector.go:11-52）：Type/Validate/ListResources（parentID 懒加载）/ResolveResourceAncestors/FetchAll/FetchIncremental。`StreamHandler.Emit` 逐条摄取限制内存、`Checkpoint` 要求 cursor 为完整可续快照而非增量（connector.go:60-75）。调度去重：robfig/cron 按绝对时间触发，多实例同分钟齐发；Layer1 `HasRunningSync` 跳过仍在跑的同步，Layer2 `TaskID="dssync:<dsID>:<minute>"` 由 Redis 保证唯一（scheduler.go:140-206）。`ProcessSync`（service/datasource_service.go:590-668）：实现 `StreamingConnector` 者走流式，全量用旧 cursor 仅作删除基线（`streamStartCursor`：用户全量首次尝试丢 cursor，超时重试保留 checkpoint，:985-991）；批量路径 fetch 失败也持久化 nextCursor（:709-715），防瞬断后整库重扫；`applyFetchedItem` 处理删除对账（限定 ds.ID+external_id 防跨源碰撞，:864-935）。

**上传入口与知识创建**。`CreateKnowledgeFromFile`（handler/knowledge.go:296）：`limitUploadBody` 在 multipart 解析之前封顶（FormFile 会先缓冲整个 body，:319-323）；service 层算文件哈希，datasource 渠道去重范围带 `datasource_id+external_id` 使重试幂等（knowledge_create.go:84-105）；本地存储按 `baseDir/tenantID/knowledgeID/<纳秒时间戳>.<ext>` 写入并经 `SafePathUnderBase` 防路径穿越（file/local.go:49-109）；multipart 临时文件由 `MultipartFormCleanup` 中间件回收（router.go:104）。URL 入口按 `isFileURL`（扩展名/显式 file_name）切换网页抓取与文件下载（knowledge_create.go:292,509）；worker 侧再执行 SSRF 复检（knowledge_process.go:3586-3599）。

### 3.3 本模块实现要点

1. **状态一致性优先于吞吐**：全管线处处幂等/防覆盖——四重 abort 检查点（进入前/chunk 写前/索引前/完成前）、`FinalizeSubtask` 用主库写 WHERE 守护而非读副本判断，围绕"任何一步失败不得把行滞留在中间态"设计。
2. **多级降级链贯穿两端**：解析侧 anydoc 类型级默认→引擎 fallback→docreader ReadStream→unary；切分侧 heading→heuristic→legacy。末端恒有输出。
3. **队列拓扑容量隔离**：六池静态划分 + shared 弹性借用（依赖 asynq 原子出队保证单次执行），长任务不得占用用户链路突发容量。
4. **fan-in 计数闭环治理**：pending_subtasks_count（DB）与多模态 Redis 计数都遵循"先种子、后 fan-out、缺口显式释放"三段式，配套死信回调与 housekeeping 双保险兜底。
5. **可观测性内建**：span tracker 记录每 attempt 的 stage/子 span 心跳，既服务 UI 时间线，又被 housekeeping/handler 反向用作卡死判定与 stallSite 定位——一套表三处消费。

## 4. 检索与索引引擎

### 4.1 功能清单

1. HybridSearch 混合检索主流程（归一 MatchCount、鉴权、同 embedding 校验、结果截断）
2. Query Embedding 一次计算并在多 store 间复用（含维度漂移校验）
3. 跨 KB 鉴权（Tenant API Key + 组织 Viewer 三维授权，拒绝返回 NotFound 防枚举）
4. 多 KB 同 embedding 模型一致性校验（name+BaseURL 指纹，wiki/graph KB 豁免）
5. store 分组 fan-out：按 (VectorStoreID, OwnerTenant) 分桶、errgroup 限流 4 并发、单组 30s 超时

7. 加权 RRF 融合（K=60，vector 0.7 / keyword 0.3，租户级可调）
8. 单路去重（按 ChunkID 保最高分）与 BM25 无界分数 rescale 到 [0,1]
9. FAQ 迭代扩 TopK 检索 + 负向问题过滤（最多 5 轮、TopK 翻倍封顶 500）
10. CompositeRetrieveEngine 组合引擎（按 RetrieverType 路由、并发 Retrieve/Index/Delete）
11. 引擎工厂与双注册表：env 引擎（RETRIEVE_DRIVER）+ DB store 引擎（singleflight 重建、30s 冷却）
12. keywords_vector_hybrid 双写索引器（单次 embed、批量 40、并发 5、base64 图片清洗、2 万字符截断）
13. pgvector 驱动：ParadeDB BM25 关键词 + HNSW 表达式部分索引向量检索（ef_search/iterative_scan/GUC 降级）
14. sqlite-vec Lite 驱动：lite_embeddings + 按维度分表 vec0 虚拟表 + contentless FTS5（CJK bigram）
15. 10 种向量引擎驱动（postgres/sqlite/es v7v8/opensearch/qdrant/milvus/weaviate/doris/tencent_vectordb）+ neo4j 图驱动
16. Embedder 抽象：本地 Ollama + 远程 4 种协议（OpenAI/DashScope/Ark/Google），并发门 + langfuse 装饰链
17. Reranker 抽象：5 种协议（Cohere/DashScope/NIM/LKEAP/Volcengine）

### 4.2 实现详解

**HybridSearch 主流程**。执行链：`HybridSearch`（service/knowledgebase_search.go:125）→ `normalizedMatchCount`（:317，<=0 回落 DefaultRetrievalTopK=50）→ `GetKnowledgeBaseByIDs` 批量加载（:153）→ `authorizeKBAccess`（knowledgebase_search_storegroup.go:199，先 `AuthorizeTenantAPIKeyKnowledgeBases` 再逐 KB `access.KBPermissions.Check` OrgRoleViewer）→ `validateSameEmbeddingModel`（storegroup.go:252，经 `ResolveEmbeddingModelKeys` 得 `name|BaseURL` 键）→ 过采 pool：`max(MatchCount*5,50)*len(KB)` 封顶 500（:193-196）→ 一次性算 query embedding 塞进 `params.QueryEmbedding`（:206-214，维度不符报 2201）→ `resolveStoreGroups` → `retrieveFromStores` → `classifyRetrievalResults` → `fuseOrDeduplicate` → `applyFAQPostProcessing` → 截断 MatchCount（:296）→ `processSearchResults`（knowledgebase_search_results.go:14，两轮 enrichment 取 parent/related chunk，图片块再取二级 parent :66-79）。

**store 分组与 fan-out**。`resolveStoreGroups`（storegroup.go:87）按 partitionKey{storeID, tenantID} 分桶，整体解析预算 12s。每组经 `retriever.CreateRetrieveEngineForKB`（factory.go:147）：无绑定 store 走 tenant `GetEffectiveEngines()`；有绑定则 `resolveBoundEngine`（factory.go:194）校验所有权（跨租户→`ErrVectorStoreForbidden`）并从注册表取引擎——DB store 引擎覆盖 tenant 级过滤（:254-259）。`retrieveFromStores`（knowledgebase_search_fanout.go:48）：单组直连快路径；多组 errgroup+`SetLimit(4)`+每组 30s 超时（:23-24/60/67）；全败即败，错误折叠 2201（:103）；仅当结果跨 >1 引擎类型才做归一（:110-129）。注册表 `GetOrLoadByStoreID`（registry.go:225）用 singleflight+代际计数（`storeGen`）防在途重建覆盖，构建超时 10s、失败冷却 30s（:24/:30）。

**融合与去重**（knowledgebase_search_fusion.go）。纯向量→`deduplicateByScore`（:68，保原始 embedding 分，FAQ 阈值依赖）；纯关键词→去重后 `rescaleUnboundedScores`（:94，`score/max`，避免 compositeScore 0.3*base 饱和）；混合→`fuseWithRRF`（:129）。RRF 公式：`score = vectorWeight/(K+vectorRank) + keywordWeight/(K+keywordRank)`（:164-169），1-indexed 排名；参数来自租户 `RetrievalConfig`（JSONB）默认 K=60、0.7/0.3（retrieval_config.go:86-109）。元数据冲突取向量侧较高分（:148-158）。

**FAQ 迭代检索**。`applyFAQPostProcessing`（knowledgebase_search_faq.go:24）：唯一块不足且向量路打满时进 `iterativeRetrieveWithDeduplication`（:73）。种子 `TopK=min(matchCount*3,500)`，每轮只改 `group.TopK`（BaseParams 不可变，`paramsWithTopK` 重建切片），不足则翻倍（:210），最多 5 轮（:78）；负向问题精确匹配过滤（:300），达标或召回数<TopK 提前终止（:193-202）。

**pgvector 驱动（性能核心）**。关键词：`KeywordsRetrieve`（application/repository/retriever/postgres/repository.go:164）用 ParadeDB `content ||| ?`（:198-201）+ `paradedb.score(id)`（:215）；BM25 索引 DDL 在 migrations/versioned/000002_embeddings.up.sql:42-43。向量：`VectorRetrieve`（:265）。HNSW 为**表达式部分索引**，DDL：`USING hnsw ((embedding::halfvec(3584)) halfvec_cosine_ops)`（000002:59-70，另有 798/1024 维变体 000059）。查询两侧必须写 `embedding::halfvec(dim) <=> $1::halfvec(dim)` 才能命中索引（:377-393）；先按 `dimension=` 过滤（匹配部分索引 WHERE）。子查询 LIMIT 为 `expandedTopK`（TopK*2，钳 [100,200]，:350-359）；阈值换算 `distance <= 1-threshold`（:396）。事务内 `SET LOCAL hnsw.ef_search=expandedTopK`（:412-419）与 `SET LOCAL hnsw.iterative_scan=strict_order`（pgvector>=0.8，:427-431）；GUC 不支持则回退裸查询（:438-443）。得分 `(1-distance)`（:380）。

**sqlite-vec（Lite 模式）**。`NewSQLiteRetrieveEngineRepository`（retriever/sqlite/repository.go:43）：`lite_embeddings` 元数据表 + 按维度懒建 `vec_embeddings_<dim>` vec0 虚拟表（`distance_metric=cosine`，:108-126）；FTS5 contentless 表 + CJK bigram 手工分词（:62-102）。`Retrieve`（:266）可同时执行两路；关键词得分 `bm25(fts)*-1000000.0`（:300）；向量路 `MATCH ? AND k = ?` 子查询过滤后 `ORDER BY distance`（:382-409）。

**双写索引器与引擎组装**。所有驱动均包成 `NewKVHybridRetrieveEngine`（keywords_vector_hybrid_indexer.go:50）。其 `Index`（:70）仅当 retrieverTypes 含 Vector 才计算 embedding 一次传给仓储层 Save——关键词/向量"双写"在同一存储内由各驱动 Save 保证（如 sqlite 三表同步写 :144-158）。`BatchIndex`（:88）：5 次指数退避 embed + 批 40 + 信号量并发 5（:106-117）；`sanitizeForEmbedding`（:160）清 base64 图片为 `[image]` 并截断 20000 字符。`CompositeRetrieveEngine.Index`（composite.go:198）对各 engineInfo 并发下发。`IndexingStrategy`（types/indexing_strategy.go:11-31）是 KB 级 vector/keyword/wiki/graph 四开关，控制入库管线与检索参数生成。

**Rerank 插件与图谱**。`PluginRerank.OnEvent`（chat_pipeline/rerank.go:38，CHUNK_RERANK）：空结果且阈值>0.3 时降阈值 0.7x 重试（:148-179）；compositeScore=`0.6*model+0.3*base+0.1*sourceWeight` 钳 [0,1]（:439-455）；`applyMMR`（:458，λ=0.7）：预计算 token 集 Jaccard 为冗余度，`mmr=λ*rel-(1-λ)*red` 贪心增量选择（:483-517）。图谱：入库后置任务派发 graph chunk → `ChunkExtractService.Handle`（extract.go:224）→ `graphBuilder.BuildGraph`（LLM 抽实体/关系+权重度数）→ `Neo4jRepository.AddGraph`（neo4j/repository.go:46）；检索两路：chat_pipeline `PluginSearchEntity`（search_entity.go:75/106）调 `SearchNode`（neo4j/repository.go:164，Cypher CONTAINS 匹配）；Agent 工具 `query_knowledge_graph`（agent/tools/query_knowledge_graph.go:73）并发查多个 KB（上限 10）。

### 4.3 本模块实现要点

1. 正确性优先的防御设计：embedding 维度漂移前置校验（knowledgebase_search.go:61）；多 KB 跨租户鉴权防 KB UUID 枚举（storegroup.go:199）；store UUID 永不进用户可见错误（factory.go:16-18）。
2. RRF 只在混合路启用，单路保真：纯向量保原始 cosine 分、纯关键词 rescale 防饱和，RRF 参数租户级可调。
3. pgvector 表达式部分索引是性能核心：无固定维 halfvec 列 + 每维度部分索引，查询表达式必须逐字匹配才走索引；ef_search/iterative_scan 在事务内 SET LOCAL 且带老版本降级。
4. 并发与资源上界无处不在：检索 pool 封顶 500、fan-out 4 并发/30s、引擎重建 10s/冷却 30s、embed 并发门+5 次退避——所有用户可控 TopK 都被钳制。
5. 双注册表架构：env 引擎（byEngineType）与 DB store 引擎（byStoreID，singleflight 按需重建）并存，KB 绑定 store 时显式覆盖租户默认路由。

## 5. Agent 系统（ReAct 引擎与工具体系）

### 5.1 功能清单

2. 版本模型是追加式不可变快照 + 修剪请求，回滚即"把旧 revision 写回为新版本"，不存在原地修改。
3. 链接一致性由工具层维护（rename/delete 联动改链/清死链），存储层只存邻接表。

## 9. 跨会话长期记忆

### 9.1 功能清单

1. 五类记忆：profile/preference/fact/task/interest（interest 由复现度派生，用于调理检索而非复述）
2. 三种来源：explicit（用户明说）/extracted（后台抽取）/manual（记忆管理器手工）
3. 四种状态：active/superseded/archived/pending——**inferred 项保持 pending 直到用户确认，绝不注入 prompt**
4. 后台抽取任务（TypeMemoryExtract）：会话级 slot、转录分段、JSON schema 输出
5. 注入分级：常驻 profile/preference 块每轮注入；情境 fact 词法+语义双路召回
6. 召回融合：lexical（bigram Jaccard）+ vector（embedding）排名融合 fuseRankings
7. 记忆 embedding 回填（backfillEmbeddings）与别名向量化
8. search_memory 工具（开关注入，非白名单）
9. 文档亲和（document affinity）：用户持续引用的文档条件化偏置检索（chat_pipeline/memory_affinity.go）
10. 记忆整合（consolidate.go）：强制合并/去重/取代
11. /api/v1/memory/* API 面：设置/条目/主题/确认/导出/强制整合（full-access API key only，主体恒为调用者）
12. 隐私：用户级开关关闭（MemoryDisabledContextKey）、条目可隐藏（RedactedMemoryPlaceholder）

### 9.2 实现详解

**数据模型**（internal/types/memory.go）。五类常量（:24-33，interest 的注释明确设计意图：知道某人做医学影像，是把"怎么调分割模型"变成能找到正确文档的查询，而不是复述给用户）；来源常量（:38-42）；状态常量（:46-55，pending 注释："静默断言一个错误猜测，就是记忆功能永久失去信任的方式"）；写模式（:59+）：explicit-only 等；`MemoryItem`（:288，Status 默认 active :307）；`MemoryConfig`（:333）；`MaxMemoryPendingSessions=32`（:239）防抽取任务积压；`MemoryTopicStat`/别名（:707+）。

**抽取**（service/memory/extract.go）。`ScheduleExtraction`（:90）在会话回合后调度；`enqueueExtraction`（:145）带 slot 管理与 `releaseSlot`（:180）；`Handle`（:254）消费 asynq 任务：`collectSessionSegments`（:464）收集转录分段、`extractSegment`（:386）逐段抽取、`extractionSystemPrompt`（:570）+ `extractionSchema`（:685，JSON 强 schema）；`scheduleFollowUpIfNeeded`（:411）分段续抽；过期解析 `parseExpiry`（:228）。抽取产出默认 pending，等用户确认。

**召回与注入**。`Recall`（service.go:113）统一入口。词法路（lexical.go）：`tokenize`（:21）+ `bigrams`（:48，单汉字成词处理 :59）+ `scoreItems`（:72）+ `selectRecallItems`（:161，maxItems + runeBudget 双限）+ `takeWithinBudget`（:197）。向量路（vector.go）：`embedText`（:71）/`vectorSearch`（:200）/`embeddableText`（:136，条目+别名拼文本）/`backfillEmbeddings`（:262）。融合：`fuseRankings`（:240）合并两路排名。chat_pipeline 注入：memory_recall.go（召回）+ memory_affinity.go（文档亲和）+ 常驻块注入。

**边界与治理**。consolidate.go 整合去重；scope.go 作用域（workspace 开 + 用户开关双门）；recall_trace.go 召回可解释性。API 面 routes_memory.go（full-access API key only，主体恒为调用者——防止查别人记忆）。

### 9.3 本模块实现要点

1. 信任模型优先：pending-直到确认是不可让步的设计（memory.go:50-55 注释），二开不得把 inferred 项直接注入。
2. 召回是"常驻块 + 情境召回"两速制：profile/preference 免检索常驻，fact/task/interest 按需词法+向量融合。
3. interest 的存在是为了改写检索（文档亲和），不是展示——与 RAG 检索层有明确耦合点（memory_affinity 插件）。

## 13. 代码实现的重点（跨模块综合）

通读全部模块后，WeKnora 代码里最值得二次开发者吃透、也最能代表其工程水准的十个实现重点：

### 13.1 双形态单代码库：Redis 分布式 / Lite 单进程贯穿全层

任务队列（asynq 六池 vs SyncTaskExecutor，container.go:438-468）、StreamManager（Redis vs 内存，factory.go:18）、限流器（RedisLimiter vs 本地，container.go:722/:738）、卡死复位策略（reset_pending_tasks.go:22-31 分布式刻意不复位）全部按 `REDIS_ADDR` 存在与否分叉。**新增任何后台能力必须同时考虑两种形态**，并照惯例向 ResourceCleaner 注册停机清理（逆序执行，cleanup.go:60-78）。

### 13.2 asynq 六池拓扑 + fan-in 计数闭环

队列按负载特征分池（core 解析 / postProcess / enrichment 富化 / maintenance 维护 / wiki 硬隔离 / shared 弹性层），shared 与专池订阅同一队列靠 asynq 原子出队（BRPOPLPUSH）保证恰执行一次，且刻意排除 postProcess/maintenance 防长任务占用突发容量（router/task.go:126-136,209-215）。计数闭环统一"先种子、后 fan-out、缺口显式释放"三段式：`pending_subtasks_count` 用 `WHERE parse_status='finalizing' AND count=0` 的写守卫晋升（repository/knowledge.go:664-700，不读副本判断）；多模态 Redis 计数器先种子后入队（knowledge_process.go:4145-4240）；死信回调 + housekeeping 双保险兜底。

### 13.3 多级降级链：永远有兜底输出

三处独立降级链同构：解析侧 anydoc 类型级默认→引擎 fallback→docreader ReadStream→unary（engines.go:44-64 + grpc_parser.go:110-200）；切分侧 heading→heuristic→legacy，validator 校验失败逐级降（strategy.go:273-312）；检索侧 search_knowledge 的 mode_fallbacks（FAQ/纯向量库对 keyword 请求语义降级，search_knowledge.go:345-404）。设计哲学：**末端恒有输出，降级显式上报**（mode_fallbacks/stallSite 都是"为什么降"的可观测性）。

### 13.4 modelcontext：进模型必编码、出模型必解码

internal/modelcontext 是全库最独特的包：`Registry` 把 UUID/slug/URL 编码为请求局部句柄（cN/dN/bN/wN/msN/mtN/res://），模型调用前 `EncodeMessages`、工具执行前 `DecodeToolCalls`（per-tool key contract 校验未知句柄形状值）、流式响应用 StreamDecoder 后缀保持防半截标签（README.md 请求生命周期五步）。引用协议：模型写 `<ref id="cN"/>`，扩展为用户可见的 `<kb/>`/`<web/>`；`leaks.go` 在每个模型调用点报告存活裸 UUID。**效果：token 省了（短句柄）、引用协议稳了（跨轮不漂移）、ID 不泄漏了（防枚举）**——一石三鸟。

### 13.5 SSE「写缓冲 + 100ms 拉取」与断线续传

服务端所有事件先落 StreamManager（Redis List 或内存 slice），连接层 `handleAgentEventsForSSE`（stream.go:331）100ms ticker 增量拉取 + Flush；断线后 `ContinueStream`（stream.go:35）从 offset 0 重放并合并分帧。前端配套：fetch-event-source + 代际哨兵 + 401 无感重放 + TTFB 三点埋点（streame.ts:44-231）。**拉模式牺牲最高 100ms 延迟换来水平扩展与续传能力**——这是全系统流式架构的基石选择。

### 13.6 pgvector 表达式部分索引 + 双注册表引擎架构

无固定维 halfvec 列 + 每维度 `hnsw((embedding::halfvec(d)) halfvec_cosine_ops)` 部分索引（000002:59-70），查询两侧逐字匹配表达式才走索引，事务内 SET LOCAL ef_search/iterative_scan 带老版本降级（postgres/repository.go:350-443）。引擎双注册表：env 引擎与 DB store 引擎并存，KB 绑定 store 显式覆盖租户默认（registry.go:225 singleflight + 代际计数防在途重建覆盖）。**这是支撑"一个部署混跑 11 种向量库"的两大支柱**。

### 13.7 状态一致性优先于吞吐（摄取管线的灵魂）

四重 abort 检查点（进入前/chunk 写前/索引前/完成前）、`updateKnowledgeUnlessSourceReplaced` 防覆盖、先解析向量引擎再清旧索引（防中间失败留空文档，knowledge_process.go:403-445）、span tracker 一套表三处消费（UI 时间线 + housekeeping 卡死判定 + handler stall 提示）。近期 99 个提交里近三分之一在继续加固这一主题（stranded rows 回收、never-run 阶段取消、wiki 槽位释放）——**上游自己也在持续还这部分的债，二开改动摄取流程必须先理解这套守护**。

### 13.8 安全设计：默认拒绝 + 启动断言 + 纵深防御

API Key 策略闸默认 fail-closed（无策略即拒，api_key_gate.go:131-133）+ 启动期路由模板断言 panic（rbac.go:410，防陈旧策略静默 403）；沙箱 Docker 后端 opt-in（docker.sock 即 host root）、exec 全 uid 1000、符号链接逃逸封堵；SSRF 两道防线（创建时 + worker 侧 DNS 重绑定复检）；store UUID 不进用户可见错误；IM/embed/WS 自鉴权路由在全局 Auth 之前显式注册。**模式：宁可启动失败/默认关闭，不可静默放行**。

### 13.9 工具演进的向后兼容机制

`legacyToolSuccessors` 在注册时把旧工具名改写为新名（definitions.go:154-199），存量 agent 配置/预设/API 调用零迁移；历史消息里的旧名由 `RetiredToolReplacement` 给出替换指引。上游用这套机制完成了 knowledge_search/grep_chunks→search_knowledge 等 5 个工具的合并（CHANGELOG Unreleased）。**任何要做工具面演进的二开，直接复用这套机制而不是写迁移脚本**。

### 13.10 能力域注册替代白名单勾选

shell_exec/沙箱文件/search_memory/web_search/write_skill_file 等刻意不进 AvailableToolDefinitions——由沙箱开关、技能开关、记忆开关在运行时决定注册（definitions.go:43-93 大段注释阐述理由："一个改变不了任何东西的复选框就是说谎"）。**这是工具面治理的架构决策：开关是唯一事实源，UI 白名单只管可选能力**。

### 14.2 二次开发优先级建议

1. **本地定制落点**（最优先）：独立文件/目录集中修改（沿用 AGENTS.md 分支策略 main→local-custom 单向流）；避免改 internal 核心文件，优先用扩展点——数据源连接器（datasource/connector.go 接口）、存储 provider（service/file/factory.go）、检索引擎（repository/retriever/<engine> + engine_factory）、Agent 工具（tools/definitions.go + registry）都是干净的插件面。
2. **想接私有数据源**：实现 Connector 三方法（Validate/ListResources/FetchIncremental），尽量做 StreamingConnector（Emit+Checkpoint），调度/去重/对账删除全部免费获得。
3. **想加 Agent 工具**：定义常量进 definitions.go、实现 Execute、注册进 registry；若替换旧工具，走 legacyToolSuccessors 别名机制；工具参数若含身份引用，必须过 modelcontext 的 per-tool key contract。
4. **想调检索质量**：租户级 RetrievalConfig（RRF K/权重）→ rerank 插件参数（compositeScore 权重/MMR λ）→ KB 级 IndexingStrategy 四开关，三层都有配置面，不必改代码先试配置。
5. **部署二开**：K8s 用 helm（12 模板较薄，容易 fork 定制）；单机长期跑建议完整模式而非 Lite（队列治理/检索能力差异大）。
